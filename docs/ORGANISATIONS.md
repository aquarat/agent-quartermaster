# Organisations, services and credential sets

**Proposal for owner review · 2026-11-20.** Keep one broker and one approval queue. Give every credential a home, and make that home the first thing the owner sees before signing. The wire contract today is [API.md](API.md); the interfaces below are proposed, not available commands.

> **client-a › PaaS › staging env** · Ref `ABC123`
>
> Release `DATABASE_URL` and `APP_SECRET` (revision 7) to **personal-build**, fleet host, in a child environment. Collect once within 10 minutes. The values will still work after that.
>
> Requester's explanation (unverified): “check the staging migration”.

That card appears **only if the owner already admitted this enrollment to client-a**. Otherwise the request stops at the agent API; it cannot become an approval prompt. On an admitted host the unusual combination is visible without having to infer a client's identity from a directory or a reason.

## What the boundary buys

Design for one compromised agent session or service on one host. Routine work by trustworthy agents should take one command and, when needed, one familiar passkey tap. A fleet host is one trust domain: another process with the same uid, or an agent with local root, can use its mTLS key and observe delivered credentials. `requester.tool`, cwd, user, session and reason are context, never evidence of who or what will run. Separate host enrollments on separate machines are appropriate for mutually distrustful work.

An organisation separates **authorisations**, not bastion processes. The operator, aqmasd, its approval origin and the owner's authenticators remain trusted as in [DESIGN.md](DESIGN.md). An approval origin serving hostile JavaScript can misdescribe what it asks the authenticator to sign; the CLI Ref and applied-action push remain useful independent checks. No agents on the bastion. No new upstream privileges, multi-tenant hosting guarantee, per-process sandbox, organisation audit export, quorum or general policy language in this milestone.

## Where credentials live

| Organisation / service / set | What a grant actually permits |
|---|---|
| `personal/fleet/<target>` | `ssh-ca`: ask the existing SSH user CA for a cert for this target and one permitted login. Sets reference the signer; they do not contain copies of the CA key. |
| `personal/dns-cdn/proxy` | `cloudflare-proxy`: call one account's proxy under a resolved scope. Parent is never delivered. |
| `personal/dns-cdn/mint` | `cloudflare-mint`: mint one expiring child using the separate minter parent and a built-in template. Absent/disabled if token mode is off. |
| `client-a/paas/staging-env` | `env-set`: collect all named values of one immutable revision. Use separate sets for staging and production so one approval never releases both. |
| `club/drive/officer` | Possible future delegated, short-lived access to a cloud drive. No new credential kind works until server, CLI and UI understand it. |

A **service** identifies the authority that accepts the credentials (one account, installation, fleet CA or application). Sets describe how that authority may be used. Scopes are *inside* a Cloudflare set: no set per zone or per permission. Enrolled requesters are global identities, distinct from SSH targets. Slugs are lowercase ASCII path segments, unique among siblings; reject empty segments, slash, dot segments, aliases and fuzzy matches. Display names may be friendlier. IDs and parentage never change. Archive rather than reparent or recycle an ID or legacy alias. Moving a project means creating a new set, rotating its upstream secrets, and retiring the old set; no grants move with it.

**Approvers are people, not keys.** Map all existing passkeys to one owner principal. Creating an org installs an explicit owner membership atomically. One login, one combined inbox, existing passkey bootstrap/recovery and last-key protection; no org picker before signing. Global owner alone manages catalogues, memberships, host admission, passkeys and enrollments. A membership permits that person to decide and revoke access in that org. Later add people with separate WebAuthn user handles, their own sessions/Access identities, invitations and org-filtered reads *before* accepting a second person. Never make a second passkey a second vote. At challenge and apply resolve the actual signing key and session to the same authorised person; a host in the owner-device class is not an approver.

## Policy: admission first, then duration and approval

Admission allows a host to **ask for every set** in the org; it is not permission to collect any of them. For a hard boundary on *who can ask*, use separate orgs and check who can administer each admitted host, including by SSH. Access to the account holding its mTLS key is effectively access as that host.

1. Authenticate with the existing pinned-CA mTLS path. Resolve the leaf fingerprint to a live `hosts.id` (not CN), check expiry/revocation and derive the peer address from the connection. Resolve the path/ID in a join restricted to this enrollment's admitted orgs. Reject invisible, missing and mismatched resources alike (404), before returning metadata, counting similar requests, enqueueing, notifying, or considering auto/standing approval. Never accept an org, class or host identity asserted by requester metadata.
2. Intersect limits. Effective max = smallest of server/class ceiling, org max, set/target max and kind/scope max. For omitted TTL use the smallest applicable default within that range; refuse an empty range. Clamp agent TTL as today, show the result; the owner's signed choice can only shorten and is **rejected**, not silently corrected, if out of range. Cap standing duration separately. Deny/archive beats any allow. A new `client-a` or `club` starts empty: no hosts, no silent approvals, proposed 10 min default / 30 min max. Migrated `personal` retains the existing SSH and per-scope defaults/ceilings.
3. Distinguish **policy auto** (no prompt on each matching request) from **standing** (a signed, expiring exception created on a specific approval). Outside migrated personal, both are off until enabled by a signed owner action for the org and specific set/scope. Policy auto can only narrow the catalogue's eligible proxy scopes (`cf.read`, `cf.cache.purge`); an org cannot invent eligibility. Standing also requires the owner to choose a duration on the card. Match exact org/service/set/revision, current policy version, enrollment, observed address, kind, mode, target + user or scope + canonical params, and TTL ≤ signed max. Recheck high-risk SSH exclusions and current scope rules even on a match. No silent grant of any kind for env values, minted children, `cf.admin` or `cf.read.private`. Preserve host-wide pending limits across orgs and the M2 identical-auto-grant cap within a set.
4. **Owner devices** may receive the parallel design's longer SSH/standing ceilings only where org policy allows them. Use server-held, passkey-approved enrollment class; missing class means ordinary fleet. Never add org memberships implicitly, waive high-risk rules, or extend CF/env TTL because of class. Sign class and resulting durations. Class change/replacement invalidates affected pending decisions and rules. An allowed owner laptop with a 30-minute client cap still gets at most 30 minutes.

Apply these checks at admission, challenge, inside the grant/auto/standing transaction, after waking long-polls, at collection and on **each** proxy or snapshot call. Authorise the exact object for list, lookup, cancel and revoke too; recovery/revoke by the owner remains possible after disabling the resource. Use a shared server-side decision path for legacy and scoped routes. Re-enrolling the same name gets a new host row, ordinary class by default and **zero** admissions. No access until a new signed admission. Removing an admission atomically expires pending work and revokes that host's grants and standing rules in that org; a later re-add cannot revive them. Host revocation/replacement does this across all orgs.

An edit affecting authority (policy, class, set contents, service binding, archive) invalidates stale challenges and pending requests and ends affected standing and active grants. Grant revoke still ends the standing rule it created and the one that issued it. Stop proxy use on the next check; keep child-token deletion jobs until upstream confirms deletion or expiry. A call already forwarded can finish. Issued SSH certs still work until expiry, open SSH sessions can outlive it, and no broker operation recalls a copied env value. Show these consequences on the confirmation.

## Using and maintaining an env set

**Normal path:** `aqmas run client-a/paas/staging-env --why "check migration" -- <command>`. Optional `--ttl`; keep `--why` mandatory for non-interactive use, Ctrl-C cancellation, approve URL, Ref and child exit status. Resolve the qualified path, request the exact revision and delivery mode, wait, collect once over mTLS, then launch the command directly with a private child environment. No shell evaluation, export script, stdout secret, cache or value in argv. Resolve the executable before merging env; reject duplicate keys and collisions with inherited variables rather than silently changing their meaning. Reject process-control names (including loader, shell-startup and aqmas configuration variables); prefer a small explicit inherited environment. This protects against mistakes, not a hostile command. The parent shell's environment stays unchanged.

**File-only tool:** `aqmas env client-a/paas/staging-env --file .env --why "start staging tool"`. A foreground holder materialises the same one-shot release in a random grant directory (0700) on a verified RAM-backed, user-private runtime filesystem; regular file 0600 from creation. Link `.env` to it *only if absent*, with no overwrite/follow of existing files or symlinks. Use a trusted, owner-controlled working directory, pinned directory handles and exclusive creation; refuse unsafe parent paths. Never use the SSH cache fallback, a repo file, ordinary temp, or a user-supplied path as the plaintext target. Refuse file mode where RAM-backed storage cannot be verified; `run` remains available. Restrict file mode to a documented literal dotenv subset that the selected tool can read without expansion; refuse values it cannot round-trip safely. Never tell the user to source the file.

The holder watches grant status and a local monotonic deadline bounded by `not_after`; unlink on expiry, revoke, loss of connectivity, signal or holder exit. Remove the target first, and only the link still pointing to this holder's file. Keep non-secret cleanup metadata for an owner-only runtime reaper on startup/login; a killed holder may leave a readable target until reaped or the RAM mount disappears. Do not promise cleanup at an exact instant after a crash. Exclude the runtime directory and symlink targets from backups, indexers and file watchers. Account for swap/hibernation and core dumps in the host baseline; tmpfs alone does not guarantee bytes never reach persistent storage.

**TTL is a collection deadline, not an upstream expiry.** For `run`, the grant need not kill the child: descendants, logs, process inspection and open file descriptors can retain values. File cleanup is hygiene on a cooperative host. aqmas records who requested which revision, when, why and who authorised release; it cannot audit use at the provider. Prefer proxy grants or issued short-lived credentials. A rotation helper should list exposed revisions, recipient enrollments and outstanding grants, guide changing the value **at the provider**, then stage the replacement and retire the old value. Editing the broker alone does not rotate a database password.

**Owner writes, never browses plaintext.** Admin pages show org/service/set, key names, revision and last change. No reveal endpoint. Start with `aqmas set import PATH --from .env`, `aqmas set put PATH KEY` (hidden prompt or stdin) and `aqmas set unset PATH KEY`; a write-only web form can use the same protocol. Parse bounded UTF-8 literal assignments, no evaluation/interpolation, no duplicate names, NULs or unsupported quoting; fail with a key/line number, not the line. Limit counts, key/value lengths and total bytes. Show whether the proposal adds, replaces or removes each key. Import does not delete the source; after verifying the new set, the owner retires the old encrypted repo file, backups and keys according to their retention policy. Rotate anything previously exposed.

Use a short-lived **edit draft** so `decide` cannot substitute a different value behind identical masked dots. Owner starts the import/edit from a signed-in admin page, receiving a random, short-lived single-use upload ticket for one path, operation and base revision. Submit values from the owner's trusted CLI on the pinned connection (also require an admitted enrolled owner device for CLI uploads); store only the ticket hash, never put it in a URL or argv. Stage encrypted, bounded data, with no effect on the live set; only that web session may challenge it. Expire unused drafts. For an edit, the submitting tool generates a fresh secret 256-bit salt and computes SHA-256 over a versioned length-prefixed encoding of salt, immutable path IDs, base revision and sorted `(operation,key,exact value bytes)` entries. Send salt inside the secret payload; persist it only encrypted. The CLI shows the commitment and Ref for comparison with the card; a web form computes its own expected commitment before submission. No unsalted hash of a guessable secret in the DB, audit or browser history. The confirmation describes the names and changes, not the values; the digest binds bytes, it does not tell the owner they typed the right password. At apply decrypt and recompute, verify base revision and exact manifest, commit the new revision and consume draft atomically.

Bind each draft and upload ticket to the draft ID, session, admission generation and base revision as well as its path. Removing and re-adding the host must not make an old ticket work again. Purge the draft and its wrapped data key at commit, cancellation or timeout. On superseding a revision, retain the manifest and delivery history but drop the old blob/key when no longer needed for issuer cleanup. Backups made earlier can still decrypt it until they and their recovery keys age out.

## Secrets on the bastion

Today the SQLite store has no bearer values. `setupCloudflare` reads two separate printable tokens at start from systemd `LoadCredential=` or the existing uid/mode-checked file option. M2 persists upstream child IDs, not child values. Keep CA private keys in their existing protected files. For env revisions, drafts and imported CF parents, encrypt **before SQLite** (including its WAL, journals and temp tables). Persist metadata such as names, recipients, reasons and timestamps in clear; treat the database and redacted CF snapshots as sensitive even without keys.

Use a versioned envelope: one random 256-bit data key per immutable secret blob, authenticated encryption (XChaCha20-Poly1305 with a fresh random 192-bit nonce) for the payload and separately for wrapping the data key under the active master key. Bind authenticated associated data to format/purpose, org/service/set IDs, kind, revision and blob role (draft, values, proxy parent or minter parent); on unwrap also bind key ID. Reconstruct these fields from the expected authorised object, not from the ciphertext header alone. Never reuse nonces or share a parent credential between roles. Keep decryption at point of use; no decrypt/list-all diagnostic. Disable body tracing/core dumps, restrict ptrace and swap, clear transient buffers where possible (Go/runtime copies cannot be guaranteed wiped). No values in challenge text, audit, snapshots, pushes, panic messages or example config.

Provision the independent random master key out of band, preferably as a systemd encrypted credential unsealed into `$CREDENTIALS_DIRECTORY` at startup; a separately protected root-only key file delivered by `LoadCredential=` is a simpler fallback. Never place it in SQLite, the repo, environment strings or a DB backup. Never generate a replacement on startup. Missing/wrong key, unknown format or authentication failure locks secret operations and alerts the owner; no plaintext fallback. A DB-only thief gets metadata and ciphertext. A running-process or root compromise gets keys and plaintext and can act as the broker across orgs; envelope encryption and passkeys do not fix that compromise.

Back up a consistent SQLite online backup, config, CA material and any retained snapshot files, encrypted with independent backup credentials. Escrow required master **key versions** separately under owner control, including a portable recovery copy if hardware-sealed. Test restoring and authenticating every live blob in isolation, without minting or serving. Loss of all copies of a master key means recovering values from issuers. For routine master rotation provision both keys, wrap new writes with the new one, rewrap each data key transactionally and resumably, verify inventory and backup restore, then retire the old online key. Keep separate recovery keys for retained backups. Suspected disclosure calls for new upstream values/parents and data keys, review of grants/host and passkey trust, and revocation at issuers; rewrapping cannot protect an old backup already stolen.

At key provisioning, store a small authenticated key-check record bound to the installation and key version. Verify it before accepting even the first post-restart secret write. A locked store still permits signed revocation and queues issuer cleanup; it cannot release secrets or report a child deleted until confirmed.

## Wire contract and approval UI

Keep agent and web listeners separate. Propose `/v2/catalogue` (admitted paths and IDs only), `/v2/requests` (org/service/set IDs, expected revision, existing typed request payload or env delivery mode, TTL, reason, requester), and versioned status/cancel/grant-list views. Use the existing long-poll pattern. Return the resolved path, IDs, kind, revision and validity for CLI comparison; mismatched parents, mode or grant kind fail closed. Add `aqmas sets [ORG]`, scoped `status`/`list` and an explicit `--service ORG/SERVICE` for CF tools. Never infer an org from cwd. Keep global enrollment, login and update distribution global.

Env status and list endpoints return metadata **only**. `POST /v2/grants/{id}/collect` is the sole env release path: live issuing host ID and same peer address, current admissions/policy, matching active grant/revision/mode, before expiry. Atomically mark consumed and audit release before returning names/values once with `Cache-Control: no-store`. Simultaneous calls cannot both win; lost response requires a fresh approval. CLI verifies exact grant ID, manifest and revision before use. Browser decision responses and host `status --json` must never serialize that response type. Do not copy the M2 child-token cache/print options for env sets.

Give each CF service a catalogue, proxy base path, proxy/minter credential handles, resource map, protected-host rules and snapshot namespace. Select the service *before* selecting a grant or injecting a token. Reject mixed-service grant lists, scope hints and synthetic account responses outside the service. Filter shim refresh, implicit read requests, grant reuse, account discovery and token caches by service. Scope snapshot lists, IDs, sensitive-scope checks and pruning by service and original host **ID**, not merely host name; preserve M2 redaction, private-scope restrictions and same-host visibility. Scope in-memory tunnel versions, permission caches and child deletion/reconciliation by service/issuer too. Do not delete a token in another service because its name looks orphaned. Require a dedicated upstream account/credential authority per org, with provider-limited parents; a broad parent, including for account-wide list or admin calls, cannot provide a narrower org boundary merely by renaming it. Defer additional CF accounts until these checks hold.

**Canonical v2.** Extend the Go builder/parser and TS verifier together. Retain [API.md's challenge rules](API.md#approval-challenge-the-security-boundary): flat, sorted UTF-8 JSON with exact scalar keys, SHA-256 challenge, fresh nonce, two-minute single-use challenge bound to session, endpoint, verb and object; WebAuthn user verification, origin/RP checks. Dispatch on `(v,object,action,kind)`; unknown kind, missing/extra key, duplicate or noncanonical byte encoding is an error. No negotiated downgrade of a scoped decision to v1. A stale page must refuse and reload.

| Actions | What the signature binds, beyond `v,object,action,id,issued_at,nonce` |
|---|---|
| `request` approve/deny, `grant`/`standing` revoke | Full org/service/set IDs and signed slugs/titles, resource and policy revisions, kind, enrolled host ID/name/class and observed address; retain **all** applicable SSH or CF fields and TTL/standing semantics from API.md §§2, 5.4. Env adds revision, sorted key manifest and delivery (`process` or `file`). |
| SSH and CF access details | Pin the resolved authority, not just a name: SSH CA/key fingerprint, target address/port, pinned host-key fingerprint (or explicit missing pin), effective principal and cert profile; CF account ID, resolved resource IDs, scope/params/mode, template permissions/resources and IP condition for mint. Changes to config/guard rails/catalogue or signing profile require a new service revision. |
| `organisation`, `service`, `credential_set` create/edit/archive | Parent IDs and labels to the applicable depth, allocated object ID even for create, expected old revision (0 for create), old/new slugs/titles, kind, full typed public configuration diff, resulting revision. Org creation includes initial owner and policy. Secret-bearing edits additionally sign draft ID, edit commitment and sorted key operation manifest. No unspecified side effects or untyped JSON patch. |
| `org_policy` replace; `org_host` admit/remove | Org ID and signed label, expected policy revision, old/new defaults, maxima, standing limits and exact set/scope/mode selections changed. Admission/removal signs exact host row ID, cert fingerprint, name, class, effect and old/new membership. No wildcard host names. |
| Future `org_approver` add/remove; host class | Org ID/label, person ID/display identity, exact role and previous/new membership revision. Keep owner membership protected. Enrollment/class actions remain global, explicitly signing class, CSR/enrollment identity and replacement identity; do not bundle implicit org access with enrollment. |
| `migration` activate | Personal org/owner IDs, source schema and config fingerprint, selected host IDs/fingerprints, exact mappings, policies/auto rules and retirement of outstanding authority. Sign one bounded plan; refuse oversize plans in the first release. No activation by a bare config flag. |

Lists/manifests above are scalar strings with a specified per-action encoding: sorted restricted identifiers for names, otherwise canonical typed records encoded as a string (fixed field set and byte order; parse and reserialize in both languages). Before shipping each action publish its exact schema and positive/negative vectors in API.md. The UI checks the entire card and choices against the parsed canonical, checks its hash against the options, then renders **from those signed fields**: org first, destination and requesting host distinct, visible IDs/Ref, duration, risk, mode and standing/auto consequences. Decode structured fields into human-readable rows; never ask the owner to approve an opaque config hash. Keep escaping/bidi isolation and independent CF scope descriptions, including where minting is broader than proxying. Reason and command are untrusted context; neither restricts use.

Use session-protected `/api/ui/` read views and the existing `challenge` → `decide` pattern for admin changes. Never accept replacement values/config at decide. Reparse stored canonical, compare all immutable bindings, signing identity, membership and current versions, then apply exactly once in an immediate transaction with append-only audit. Stale (rename, rotation, concurrent revoke or config change) → 409, require fresh review. Auto decisions reference the exact signed policy/rule; collection is execution of a grant, not another owner decision. Push the applied org/path, action, duration and Ref to the owner; never send key values or free-form reasons. Add admin pages for org policy/admissions, services and sets/revisions, and a server-side org filter for Activity (including a separate global/legacy view). Keep counts, recent-similar queries, notification recipients and future approver views within authorised orgs; a client-side filter is not access control.

## Cutover and delivery order

1. **Inventory and dry run, personal only.** Append migrations after the current `PRAGMA user_version` 4 (coordinate numbering with owner-device work). Generate a repeatable plan from a consistent backup and validated config: one personal org, one owner, live enrollment IDs admitted to personal only, `[[targets]]` → fleet sets, optional `[cloudflare]` → one service and its mode sets. Carry principal, users, host key, TTL/risk and all scope narrowing, named-ID bindings, IP conditions, deny/guard rules and snapshot settings forward. Disabled features stay disabled. Retain the SSH CA, global principal uniqueness, client TLS pins, enrollment certificates, RP ID and passkey handles. No [host trust](HOSTS.md) change.
2. **Review then activate.** Stage schema and catalogue metadata without issuing new authority. Keep personal-only legacy operation until cutover. Before signing the final plan, pause mutations, fence and drain polls, mints, proxy calls and sweepers, and make a consistent recovery point. Recheck source versions and host inventory in the activation transaction; abort on drift. Initially leave CF parents behind fixed personal service handles using the existing loader. Pin the public config revision; changed role mappings, account or policy require signed review, never an unsigned live override. Operational settings like listeners stay in config.
3. **Backfill and close old authority.** Preserve IDs, SSH serials and sequence high-water mark, validity and deletion records. The historic CF rows have no issuer/account ID; current config and a matching scope are not proof of origin. Use verified issuer inventory or operator records, and verify reused SSH target names too. Keep ambiguous records owner-only, inert and unassigned; report unresolved children through expiry, don't try another minter. Expire pending requests and v1 action challenges; revoke legacy standing approvals and active broker grants. Report delivered certs outstanding until expiry and reconcile verified children with the original minter. Index old snapshots only when service and original enrollment are proven from grant history; otherwise archive owner-only. Don't rewrite append-only audit rows: attribute legacy events via verified object-ID joins or show separately. An audited atomic activation marker selects the new path on restart.
4. **Compatibility gate.** `/v1/requests`, polls, lists, CF paths/catalogue/snapshots and `/v1/ssh-ca` resolve *only* immutable migrated personal aliases. Require route namespace, active admission and enrollment ID in store lookups **before constructing status or minting**, including when the host is admitted to both orgs. An old CLI uses personal SSH/CF without changes; unknown aliases fail. Qualified paths on a v1-only server get “upgrade required”, never a stripped request. Namespace new SSH/CF caches by server pin, enrollment, org/service/set ID, revision and target/scope. Ignore unscoped caches in v2; no offline reuse for scoped access. Old clients can still reuse unexpired personal SSH certs offline. [UPDATES.md](UPDATES.md) is separate; don't require simultaneous agent upgrades.
5. **First useful addition:** pilot one client env set (`run`, trusted CLI import, rotate, revoke). Gate on Go/TS canonical interop, pre-M2 and current DB fixtures, wrong-key restore, interrupted rewrap, and two-org tests with identical names. Exercise stale signatures, remove/re-add, dual-admitted host on v1, parallel collection and mixed grant headers (same failure for foreign and unknown IDs). Check logs/WAL/output with sentinel values. Add RAM-file delivery only after platform cleanup tests. Move CF parents into encrypted storage in a **separate** signed cutover: stage the existing loader's bytes as role-specific blobs, bind commitments, verify reader and restore, switch references, retire old sources and rotate upstream. No second CF account until service scoping and cleanup are tested.
6. **Later kinds.** A git host, project-management service or drive can add `http-proxy` sets with fixed upstream origin, header slot, allowed routes/methods and redaction; prohibit arbitrary URLs, redirects and caller-supplied auth headers. An `oauth` set pins issuer, client, audience, subject, scopes and token lifetime; keep refresh credentials encrypted on the bastion and return only scoped short-lived access (or proxy it). Each needs typed canonical fields, independent UI descriptions, provider-specific revocation and safe delivery tests. Defer delegation, additional signers and audit export until needed.

**Release gate for minting.** Record an issuer-bound mint intent before the upstream call. On completion record the upstream ID and recheck live admission, service revision, grant and deadline before returning a value. Withhold on failure and queue deletion; reconcile a crash between mint and ID recording using the exact intent and issuer. Disable mint entirely if a required restriction is enforced only by the proxy (for example, limiting D1 access to one database). A warning cannot narrow an upstream token.

**Rollback.** Restore an older binary only with its matching pre-activation recovery point and proof no intervening authority changes are lost. Otherwise fix forward. On disaster recovery reconcile issuer tokens, host revocations, passkeys and rotated secrets in isolation; expire sessions/challenges/rules/grants and review admissions before reopening. Preserve post-backup audit separately. Never serve a stale allow-list.

## Appendix: SQLite sketch

Logical columns, not DDL. Keep STRICT tables, foreign keys, WAL, UTC Unix milliseconds and immediate transactions. Opaque IDs externally; retain numeric `hosts.id` and grant serials internally. Make parent+child tuples unique for composite FKs; do not store independently writable org IDs beside a set ID. Reject invalid kind/role combinations in both store constraints and handlers.

| Relation | Key columns and constraints |
|---|---|
| `people`, `org_approvers` | Person ID, unique WebAuthn handle, owner flag (one); `passkeys.person_id` FK. Membership PK `(org_id,person_id)`, role, revision. Session continues to reference login passkey. |
| `organisations`, `org_hosts` | Org ID, unique slug, title, policy revision, archived. Admission PK `(org_id,host_id)` → exact enrollment-backed `hosts` row, active flag and monotonic generation retained across removal. Sign expected generation on admit/remove; bind it in scoped actions and tickets. No inheritance by replacement. |
| `org_policies`, `org_rules` | `(org_id,revision)` immutable defaults/max per use and standing ceiling; eligible `(org_id,revision,set_id,scope,mode,auto_allowed,standing_allowed)` entries. No rule means no silent access. |
| `services`, `credential_sets` | Service ID, org FK, slug/title, provider type and immutable config revision; set ID, service FK, slug/title, kind, current revision, archived. Unique `(parent_id,slug)` at each level. Provider config revisions contain public bindings and role-specific secret references only. |
| `set_revisions`, `secret_blobs`, `edit_drafts` | `(set_id,rev)` immutable manifest, service revision, optional encrypted payload reference. Blob: role, format/key ID, wrapped key and wrap nonce, ciphertext/tag and nonce. Draft: session, exact parent IDs, base rev, ticket hash, manifest/commitment, blob, expiry and consumed marker. Retire old plaintext capability; keep revision metadata for audit, not indefinite decryptable history. |
| `requests`, `grants`, `standing` | Add bound set revision, policy revision and service revision; derive org from immutable ancestry or enforce consistency by composite FK. Retain host FK, peer, typed M1/M2 fields, `grants.request_id` unique, `standing.source_request_id`, `requests.standing_id`. Env adds delivery mode and `consumed_at`; CF deletion work includes issuer/service binding. Index live lookups by host + set + exact match fields. |
| `audit`, snapshot index | New audit rows carry nullable org/service/set IDs, revision, host/person and signing key ID or signed rule reference, action, request/grant Ref and time. Link reason via request ID; warn never to include secrets there. Snapshot metadata links service, original grant and enrollment; no parent tokens or env payloads. Keep global security events global and retain audit update/delete prohibitions. |
